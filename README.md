# 异常开药调查证据室

约定异常开药（疑似倒药）调查中的材料来源、取证授权、候选对应、
阶段结论与移交轨迹。代码库只负责读取、登记与按规则校验这些资料，
业务服务可沿用相同的领域标识和版本约定。

## 为什么不能只凭一条同日开药记录

宜宾监管人员拿到疑似倒药人员名单后，单条同日开药记录可能属于正常患者，
也可能因过早接触对象而打草惊蛇。真正形成判断要把历年结算、取药监控、
药品追溯、资金和物流材料放到同一案件脉络中相互印证。本仓库把这条
办案常识固化为可执行的规则：

1. **按调查假设登记对象关系** —— 先登记对象与假设（如"张甲开药、
   李乙回收转售"），材料围绕假设入室；
2. **先授权后取证** —— 每份材料必须落在有效授权的类别、小组、
   时限和最低阶段之内；补充授权须指向原授权；
3. **候选对应不自动合并身份** —— 视频片段与结算记录可建立候选
   （identity / event），未经人工复核确认，不并入同一身份组；
4. **线索升级要有跨类别印证** —— 至少两类有效材料、且存在一条
   经复核确认的联结链，才允许升级；被排除的正常患者不拖累判断；
5. **决定不可覆盖** —— 升级、补充授权、材料失效、借阅、复核结论、
   并行分析、结论提交、移交全部追加进哈希链日志，篡改即断链；
6. **最小必要可见范围** —— 各小组只能看到授权范围内的材料，
   跨部门借阅限定用途与时间窗，窗外自动收回；
7. **阶段结论冻结版本** —— 负责人提交结论时冻结所用材料的
   校验摘要，已冻结材料停止外借；报告区分**已相互印证的事实**
   与**仍只是待核的关联**，并列出每份材料冻结后的移交轨迹。

## 仓库结构

```
contracts/context.schema.json        基础资料契约
contracts/evidence-room.schema.json  证据室事件日志契约
fixtures/context.json                基础资料示例
fixtures/case.json                   全流程虚构样例案件（由生成器产出）
fixtures/build_case.py               样例案件生成器
src/context.py                       基础资料读取与字段检查
src/evidence_room/                   证据室领域模型（types/log/room）
tests/                               规则测试与契约校验
```

## 标识与版本约定

- 领域标识：`prescription-investigation`；
- 事件日志版本：`log_version: 1`；
- 材料校验摘要：`sha256:` + 64 位十六进制；
- 阶段门控顺序：`initial → corroboration → case_filing →
  prosecution_review`；
- 状态只能由事件序列重建（`EvidenceRoom.from_dict` / `to_dict`），
  没有就地修改入口。

## 虚构样例案件

`fixtures/case.json`（40 条事件）演示：

- 同日开药名单只作为线索，王丙经复核**排除**（L-02 rejected）；
- 3 月、4 月两段监控经复核确认后才与结算合并为同一身份组；
- 一份来源不清的转账截图登记后被**宣告失效**，原记录仍在日志中，
  但不进入任何结论；
- 监控组限时借阅追溯材料核对药盒批号，窗外恢复不可见；
- 两阶段结论：初查阶段区分"已认取药人"与"4 月取药人待核"；
  印证阶段认定取药、追溯、资金、物流互证的事实，同时把第二收件
  地址如实留为待核关联（L-07 candidate）；
- 冻结后资金、物流材料移交负责人档案柜，报告可说明每份材料
  后来被谁接管。

重新生成：

```bash
python fixtures/build_case.py
```

## 本地校验

```bash
pip install -r requirements.txt
python -m pytest tests/
```

所有示例均为虚构数据：人名（化名）、单位、单据号、账号信息、
监控内容与访问凭据均不对应真实个人或案件，仅用于演示证据室规则。
